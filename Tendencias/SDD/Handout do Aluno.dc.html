Prompt, vibe coding e spec-driven development

Prompt
Vive uma mensagem. Toda lacuna é uma decisão que a IA toma no seu lugar.
Vibe coding
Vive uma sessão. Rápido para descobrir se algo é possível; sem memória entre conversas.
Spec-driven
Vive no repositório. A especificação é o artefato primário; o código é a saída.

Os seis blocos de um bom prompt

Papel — quem responde, com que vocabulário.
Restrições — bibliotecas, limites, o que é proibido.
Contexto — stack, versões, o que não pode quebrar.
Formato — arquivo único, diff, tabela, JSON.
Tarefa — um verbo, um alvo.
Exemplos — um par entrada/saída resolvido.

Régua: duas pessoas competentes leriam esse pedido e construiriam a mesma coisa? Se não, a IA vai escolher por você. Ao corrigir, não repita o pedido: diga qual parte está errada e por quê.

As quatro fases do SDD

FasePerguntaSaídaPonto de verificação
EspecificarO quê e por quê, não comospec.mdA especificação está completa e clara?
PlanejarComo construir issoplan.mdO plano é viável e detalhado o suficiente?
TarefasEm que pedaços isso se dividetasks.mdAs tarefas cobrem todos os requisitos?
ImplementarCódigo, tarefa por tarefaCódigo testadoO código foi validado contra a especificação?

Três níveis de rigor

NívelO que acontece com a specQuando faz sentido
Spec-firstEscrita antes, gera a implementação inicial, depois não é mais mantida. É andaime.Exploração, ferramenta descartável. Onde quase todo time começa.
Spec-anchoredVive ao lado do código; requisito muda, a spec muda primeiro e a implementação é verificada contra ela.Quando a deriva é cara: contrato de API, vários times, sistema que precisa durar.
Spec-as-source
(spec-as-code)		A spec é o fonte; o código é gerado e nunca editado à mão.Experimental, ou domínio regulado e auditável.

Taxonomia de Birgitta Böckeler (Thoughtworks). O erro comum não é escolher o nível errado — é não saber em qual você está, e pagar o custo do nível de cima colhendo o benefício do de baixo.

As seis seções de um spec.md

Resumo — o recurso em uma ou duas frases.
Requisitos funcionais — comportamento do sistema.
Histórias do usuário — intenção e valor.
Requisitos não funcionais — segurança, desempenho.
Critérios de aceitação — fatos observáveis e testáveis.
Casos extremos — erro, fronteira, cenário raro.

Duas ferramentas — instalar em casa

# pré-requisitos: Python 3.11+, Git, um assistente de IA configurado
# uv — macOS e Linux
curl -LsSf https://astral.sh/uv/install.sh | sh
# uv — Windows, no PowerShell
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"
# CLI specify — instalação global (recomendada)
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
# uso único, sem instalar
uvx --from git+https://github.com/github/spec-kit.git specify init
# conferir
specify check
# OpenSpec — requer Node.js 20.19+
npm install -g @fission-ai/openspec@latest
cd seu-projeto && openspec init
# no chat do agente: /opsx:propose · /opsx:apply · /opsx:archive

Comando não encontrado? Feche e reabra o terminal, confira o PATH (no Windows pode ser preciso reiniciar) e rode uv tool list para ver se o specify-cli aparece. Agentes suportados: GitHub Copilot, Claude Code, Cursor, Windsurf, Amazon Q, Gemini CLI e outros — os artefatos são idênticos em qualquer um.

Os três laboratórios

Lab 1 · 20 min
Peça um validador de feed em uma frase. Liste tudo que a IA decidiu sozinha. Reescreva com os seis blocos e rode em sessão nova. Entregue prompts.md.
Lab 2 · 15 min
Vibe code um leitor de RSS. Peça uma mudança em sessão limpa e observe o que a IA desconhece. Entregue suposicoes.md.
Lab 3 · 35 min
SDD à mão, sem framework: escreva constitution.md, spec.md, plan.md e tasks.md na pasta spec/, fazendo o papel de clarify e analyze você mesmo.

Antes de virar a especificação em plano

☐ Cada história tem critério de aceitação observável.
☐ Nada descreve como implementar — só o quê e por quê.
☐ Os critérios são testáveis sem te perguntar nada.
☐ Nenhum requisito depende de conhecimento não escrito.
☐ Segurança e desempenho estão escritos.
☐ Suposições abertas estão marcadas como perguntas.
☐ Casos extremos e erros estão listados.
☐ Outro desenvolvedor entenderia sem reunião.

Trabalho para casa · duas semanas

Uma funcionalidade real levada da intenção ao código com uma das duas ferramentas, à sua escolha. Semana 1: só artefatos de intenção. Semana 2: implementação, com os artefatos atualizados pelo que você descobrir. Entrega: repositório com histórico, artefatos, código e um RELATO.md de uma página. O enunciado completo, com critérios de avaliação, está no documento do trabalho.

Spec Kit — fases explícitas, constituição formal, bom para começar do zero. OpenSpec — unidade de trabalho é a mudança, sem portões de fase, pensado para código que já existe.
